## C. Things identified along the way (beyond the plan)

### C.1 Architectural decisions locked in during this conversation

- **Cell-based deployment** is the answer for data residency (Saudi, US, China, EU), not Postgres LIST partitioning. Partitioning is a within-cluster performance optimization, not a residency mechanism. Cells = separate physical clusters in-jurisdiction.
- **Provider-aware email transport.** Resend or SMTP (SendGrid/Postmark/SES/Mailgun/self-hosted), auto-picked from env vars. Zero code change to switch providers.
- **Docker over Nixpacks/Railpack.** Railway's builder tooling has churned twice in three years; a portable Dockerfile is a one-time investment that runs identically on any container platform. Backend uses multi-stage `node:20-bookworm-slim` with `libvips-dev` + `python3` + `build-essential` for native deps (sharp, better-sqlite3), then a slim runtime image with `libvips42 + tini` running as non-root.
- **GitHub Actions is the CI substrate.** Fast suite + real-Postgres suite (with PostGIS service container) on every push. No local Node ever needed by the user again. Wired in `b9c868d`. Real-Postgres verification for every 7b.1c commit happens automatically.

### C.4 Operational lessons

- Railway's TCP proxy port is the PUBLIC port, not `:5432` — internal port is what the container listens on.
- Railway's internal DNS (`*.railway.internal`) requires Private Networking ON on BOTH services + same environment.
- Postgres `initdb` runs ONCE per volume. Changing `POSTGRES_PASSWORD` after first init does nothing — the DB keeps the original password.
- Migration ordering matters: don't edit committed migrations, always add a new numbered file.
- Password was pasted in chat during debugging. Rotation is a task. The reviewer AI catches password-in-chat too.
- The user's Windows machine has no Node — everything ran either in Codex's env or GitHub Actions. Don't ever ask the user to `npm install` or `npm test` locally.
